## Status

Vanilla JS front end (`app.js`, `api.js`, `site-builder.js`), no framework/bundler at runtime except for the rich editor and the site renderer (`editor-src/`, built with esbuild into `editor.bundle.js`/`.css` and `ssg-builder.bundle.js` — run `npm run build` after editing anything under `editor-src/` or `ssg-src/`, it's not picked up live).
No linter configured yet.

The site itself is generated by a homegrown renderer driven by [Puck](https://puckeditor.com/) (`ssg-src/`, see `docs/plan-puck-ssg.md`) — replaced the earlier Zola/Tera pipeline. Every site is built with the same fixed default Puck templates (`ssg-src/default-templates.js`, `SsgBuilder.defaultTemplates` in the browser bundle) — no per-site template storage/visual editor yet.
Content under `content/` is split into standalone pages (`content/*.md`) and blog posts (`content/blog/*.md`), surfaced as two separate groups in the "pages du site" screen (`app.js`: `listContentPages`/`renderPageGroup`).

This is a very early stage project, it's okay to break support for previously created websites, no need to suggest migrating tools each time you make a breaking change.

## Tests

e2e tests (`e2e/`) run Playwright against a real local Forgejo instance (Docker) rather than mocking API calls — see the "Tests e2e" section in `README.md` for how to run them (`npm run e2e`).
Requires Docker.

- **Docker permission denied even though `vm-setup.sh` added the user to the `docker` group**: group membership only takes effect in new sessions.
  If you're in a shell that predates the `usermod`, prefix Docker/Compose commands with `sg docker -c "..."` instead of opening a new shell (e.g. `sg docker -c "npm run e2e"`).
- **Stale, not yet adapted to the Puck renderer**: the existing e2e specs assert against Zola/volks-typo-specific markup (nav structure, CSS classes, the removed Templates tab, the ~11-15s Zola rebuild timing) — expect failures until the suite is updated to the new renderer's output. Don't take a red run here as a product bug without checking whether the assertion itself is Zola-era first.
- Tests that publish run against a **dedicated repo created via the Forgejo API in the test itself** (`site-settings-and-split.spec.mjs`, `legacy-content.spec.mjs`), not the shared `seed.repoName` — tests run with 2 workers, and two tests republishing the same repo concurrently causes real write collisions.
- If a test run flakes on something unrelated to build time (e.g. a plain API-conflict check with no rebuild involved), suspect resource contention from concurrent builds in other tests rather than a product bug — rerun once against a fresh reseed (`docker compose -f e2e/docker-compose.yml down -v --remove-orphans` then `npm run e2e:up`) before treating it as a real failure.

## Lima devbox VM

If the `CMSTATIC_DEVBOX` environment variable is set, you're running inside the Lima devbox VM created by `scripts/host-create-vm.sh`.
Implications:

- The project directory is mounted read-write from the host
- `~/.claude` is shared with the host (symlinked), so Claude Code config/auth carries over
