## Status

Vanilla JS front end (`app/app.js`, `app/providers/api.js`, `app/site/site-builder.js`), no framework/bundler at runtime except for the content editor, the site renderer, and the Puck layout editor (`editor-src/`, built with esbuild into `app/ssg-builder.bundle.js`, `app/puck-layout-editor.bundle.js`/`.css`, and `app/puck-content-editor.bundle.js`/`.css` — run `npm run build` after editing anything under `editor-src/` or `app/puck/`, it's not picked up live). `app/` is served as the app's own root (`app/index.html`, generated from `app/index.template.html`) — see README "Inclusion des packages JS".
No linter configured yet.

The site itself is generated by a homegrown renderer driven by [Puck](https://puckeditor.com/) (`app/puck/`, see `docs/plan-puck-ssg.md`) — replaced the earlier Zola/Tera pipeline. Each site can customize its own gabarits (one per route type: home/page/article/blogIndex) via the "Mise en page" screen, a full-screen `<Puck>` visual editor (`editor-src/puck-layout-editor.jsx`) — saved as `templates/<name>.puck.json` on `main` (see `LAYOUT_TEMPLATE_FILES` in `app/site/site-builder.js`), falling back file-by-file to `app/ssg/default-templates.js` for anything not yet customized. Page/article content is also edited via Puck (`editor-src/puck-content-editor.jsx`, a Config restricted to a single `RichText` component, see README "Édition de contenu") — stored as `content/<slug>.puck.json` / `content/blog/<slug>.puck.json`, injected at render time into the shared route-type template's `ContentSlot` (`app/puck/template-merge.js`). Each esbuild IIFE bundle carries its own React copy, so the component palette (`app/puck/registry.jsx`) is deliberately re-imported into `puck-layout-editor.bundle.js`/`puck-content-editor.bundle.js` rather than reused from `ssg-builder.bundle.js` — hooks (`useContext`) must run under the same React instance driving the render, see the README section "Éditeur de mise en page Puck" before touching this wiring.
Content under `content/` is split into standalone pages (`content/*.puck.json`) and blog posts (`content/blog/*.puck.json`), surfaced as two separate groups in the "pages du site" screen (`app/app.js`: `listContentPages`/`renderPageGroup`).

This is a very early stage project, it's okay to break support for previously created websites, no need to suggest migrating tools each time you make a breaking change.

## Tests

e2e tests (`tests/`) run Playwright against a real local Forgejo instance (Docker) rather than mocking API calls — see the "Tests e2e" section in `README.md` for how to run them (`npm run e2e`).
Requires Docker.

- **Docker permission denied even though `vm-setup.sh` added the user to the `docker` group**: group membership only takes effect in new sessions.
  If you're in a shell that predates the `usermod`, prefix Docker/Compose commands with `sg docker -c "..."` instead of opening a new shell (e.g. `sg docker -c "npm run e2e"`).
- **Content editor interactions**: typing into a page/article's RichText field in e2e specs must go through `tests/editor-helpers.mjs`'s `typeInRichTextEditor()` — select the block, type into its sidebar field (not directly in the canvas, see README "Édition de contenu"), and wait for Puck's own ~200ms onChange debounce before acting on the result (e.g. clicking "Publier"). Don't hand-roll `page.locator("#editorMount [contenteditable=true]").click()`: a zero-size "ghost" overlay and a still-loading `EditorFallback` both match that selector without ever syncing back to Puck's data — see the comment at the top of `editor-helpers.mjs`.
- Tests that publish run against a **dedicated repo created via the Forgejo API in the test itself** (`site-settings-and-split.spec.mjs`, `legacy-content.spec.mjs`), not the shared `seed.repoName` — tests run with 2 workers, and two tests republishing the same repo concurrently causes real write collisions.
- If a test run flakes on something unrelated to build time (e.g. a plain API-conflict check with no rebuild involved), suspect resource contention from concurrent builds in other tests rather than a product bug — rerun once against a fresh reseed (`docker compose -f tests/docker-compose.yml down -v --remove-orphans` then `npm run e2e:up`) before treating it as a real failure.

## Lima devbox VM

If the `CMSTATIC_DEVBOX` environment variable is set, you're running inside the Lima devbox VM created by `scripts/host-create-vm.sh`.
Implications:

- The project directory is mounted read-write from the host
- `~/.claude` is shared with the host (symlinked), so Claude Code config/auth carries over
